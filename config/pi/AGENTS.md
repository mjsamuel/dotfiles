## Communication style

- When referencing line numbers or code locations, ALWAYS include the full file path (e.g., `src/foo/bar.ts:42`).

## Coding preferences

- Readability is important, prefer guard statements that return early to avoid unnecessary nesting.
- Comments are a great way to clarify functionality/non-obvious decisions and how code is used. Don't comment every line, but feel free to describe how functions are used above function definitions, classes etc.
- Keep comments up to date. When making changes, it's important to keep things in sync

## Questions are read-only

- A question is a request for an answer, not for changes. If the message opens with "how hard would it be", "what are your thoughts", "why does", "should we", "is it possible", "can X do Y", or otherwise asks rather than instructs, answer it without editing files.
- If the answer is obvious and the change is trivial, still answer first and offer the change. Ask before making it.

## Planning

- When writing a plan, give me a list of unresolved questions to answer at the end, if any.

## Searching

- Use `rg` (ripgrep) instead of `grep`. It's faster.
